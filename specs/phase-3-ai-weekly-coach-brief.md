# Phase 3 — AI Weekly Coach Brief — Build Spec

**Source:** VIK-9 ("Write a real Phase 3 spec, then build the AI weekly coach
brief"). Written 2026-09-02 under demo time pressure — see "Scope decisions"
below for the calls made specifically to keep this buildable before the
upcoming Android + web demo, and why they're not a permanent architecture
choice.

**Depends on:** Phase 2.5 (coach dashboard — `/clients/[accountId]`), which
is done. Doesn't depend on Phase 2 (health aggregator) beyond what's already
flowing through `lib/stats.ts`'s `weekStats()`.

**This pass covers:** a coach-facing "AI weekly brief" per client — the
coach clicks a button, gets an AI-drafted summary of that client's week
(adherence, trends, flags), edits it if needed, and approves it. The
existing client-facing, ungated "Weekly Analysis" (`components/
WeeklyAnalysis.tsx`, `/api/analysis`, shown on the client's own dashboard)
is a **different, pre-existing feature and is explicitly out of scope** —
see "Relationship to the existing Weekly Analysis feature" below for why
these are two things, not one.

---

## Scope decisions (made 2026-09-02, demo-driven)

**Trigger: on-demand button, not a scheduled job.** The original Phase 3
milestone description assumed a scheduled weekly cron job. Decided with Vik:
for the demo, an on-demand "Generate brief" button (same interaction pattern
as the existing check-in draft generator and `WeeklyAnalysis`'s "Generate
analysis" button) tells the full "AI drafts, human approves" story live on
stage without needing real scheduling infra (job state, failure handling,
timezone-aware cron). Scheduling is real, deferred work — see "Explicitly
deferred" below — and can be added later as a thin wrapper that calls the
same generation function on a timer; it doesn't change the review/approve
data model or UI built here.

**Approved brief becomes visible on the client's own dashboard.** The PRD's
one-paragraph product description says the AI layer "drafts the coach's
weekly check-in and analysis, always reviewed and approved by the human
coach before a client sees it." Read literally: the brief is *for* the
client, gated behind coach approval. Once approved, it renders on the
client's own dashboard (`app/page.tsx`) as a new "This week from your coach"
card. Before approval, it's visible only on the coach's per-client view.
**If time is tight before the demo, this client-visibility piece is the
first thing to cut** — the demo narrative itself is the coach-side
generate → edit → approve flow; showing the client-side result is a nice-to
-have, not what carries the story. Sequenced last for exactly this reason —
see "Recommended sequencing."

## Relationship to the existing Weekly Analysis feature

`components/WeeklyAnalysis.tsx` + `/api/analysis` + `lib/ai/analysis.ts`'s
`generateWeeklyAnalysis()` already exist and already do something adjacent:
a plain-language weekly write-up, grounded in the same `WeekStats` this spec
uses. But it's a **different feature**, not a redundant one:

- It's generated by the **client, about themself**, on their own dashboard,
  with **no coach gate** — the client clicks "Generate analysis" and sees
  the output immediately.
- It's **first-person-adjacent, client-facing tone** ("how your week went"),
  not a coach's internal read on a client.
- It **predates** the "reviewed and approved by the human coach before a
  client sees it" principle in the current PRD — that's a real inconsistency
  worth naming, but retrofitting an approval gate onto an already-shipped,
  already-demoed Phase 1 feature is out of scope here. Don't touch it. If
  it's worth unifying with the coach brief later, that's a follow-up
  decision for whoever picks this up next, made deliberately — not a side
  effect of this pass.

This spec builds a **new, separate** artifact: a brief written *to the
coach, about a client*, gated behind explicit coach approval before the
client ever sees it. Reuses `lib/stats.ts`'s `weekStats()` and the
`dataAnswers()`/grounding pattern already proven in `lib/ai/analysis.ts` —
same "narrate the numbers, never invent them" discipline — but is a
distinct table, distinct generation function, distinct UI.

## 1. Data model

New table, `coach_briefs`, mirroring `check_ins`' shape (`lib/db/
schema.ts:273`):

```ts
export const coachBriefs = pgTable(
  "coach_briefs",
  {
    id: serial("id").primaryKey(),
    accountId: accountIdColumn(), // the CLIENT this brief is about
    weekStart: date("week_start").notNull(), // Monday of the week covered
    status: text("status").notNull().default("draft"), // 'draft' | 'approved'
    content: text("content").notNull(), // AI-drafted, coach-editable
    generatedAt: timestamp("generated_at", { withTimezone: true }).notNull().defaultNow(),
    approvedAt: timestamp("approved_at", { withTimezone: true }),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [uniqueIndex("coach_brief_account_week_idx").on(t.accountId, t.weekStart)],
);
```

Regenerating overwrites the same row (like `check_ins`' upsert-on-`(accountId,
weekStart)` pattern) — a coach hitting "Generate" twice for the same week
replaces the draft, it doesn't pile up duplicates. Regenerating an
**approved** brief resets `status` back to `'draft'` and clears
`approvedAt` — a fresh AI draft was never actually re-approved, don't let a
stale `approvedAt` timestamp imply otherwise.

`accountIdColumn()` gives the same `NOT NULL` + `ON DELETE CASCADE` pattern
VIK-78 already applied everywhere else — no new class of scoping bug to
introduce here.

## 2. AI generation — `lib/ai/brief.ts`

New file, new function, reusing what already exists rather than
duplicating it:

```ts
export async function generateCoachBrief(
  stats: WeekStats,
  settings: Settings,
  clientName: string,
): Promise<string>
```

- Reuse `lib/ai/analysis.ts`'s `statsBrief()` (currently unexported —
  export it) for the same grounded, numbers-only JSON payload
  `generateWeeklyAnalysis` already sends. Don't re-derive that shape twice.
- **Different system prompt**, coach-facing not client-facing: "You are
  writing an internal weekly brief for a coach about one of their clients.
  Summarize adherence (macros, water, sleep, training) vs. targets, note
  the weight trend vs. target, and flag anything that needs the coach's
  attention (missed logging, adherence drop, a protocol that may need
  adjusting). Address the coach, refer to the client by name
  (`${clientName}`), third person. Short paragraphs or a tight bulleted
  list — this is a working document, not client-facing copy yet. Only
  reference numbers present in the data; call out missing data explicitly
  rather than guessing."
- Same `client.messages.create(...)` pattern as
  `generateWeeklyAnalysis`/`generateCheckinDraft` — `thinking: { type:
  "adaptive" }`, `max_tokens: 16000`, extract `response.content` text
  blocks.

**Test plan (write first):** mock `lib/ai/client`'s `getAnthropic()` the
same way `tests/extract.test.ts` does (see VIK-84's approach — mock at the
`messages.create` seam, not the whole module's output, so the real prompt-
construction code runs). Assert: the client's name and at least one real
number from a fabricated `WeekStats` fixture appear in the generated
prompt payload sent to the mock (i.e. the function is actually grounding
on `stats`, not just calling the API with nothing).

## 3. API routes — `app/api/clients/[accountId]/brief/route.ts`

Coach-only (mirrors the existing per-client route pattern in `app/clients/
[accountId]/page.tsx:41-48`: require a session, require `role === "coach"`,
resolve the target via `getClientAccount()` so a non-client `accountId`
404s rather than silently working).

- **`POST`** — generate. Body: `{ weekStart }` (defaults to the current
  week's Monday via `mondayOf(todayLocal(...))` if omitted, same as
  `/api/analysis`). Runs `weekStats()` + `getSettings()` for the target
  client, calls `generateCoachBrief()`, upserts into `coach_briefs` with
  `status: 'draft'`. Returns the brief row.
- **`PUT`** — edit and/or approve. Body: `{ weekStart, content, approve:
  boolean }`. Updates `content`; if `approve` is true, sets `status:
  'approved'`, `approvedAt: new Date()`. Editing an already-approved brief
  without `approve: true` is allowed (coach fixing a typo post-approval)
  but doesn't touch `approvedAt`.
- **`GET`** — fetch the current week's brief for a client (or a given
  `weekStart` query param), for page load / refresh.

**Test plan:** mirror `tests/checkins-route.test.ts`'s structure —
account-scoping (a coach can't generate/fetch a brief for another coach's
client once multi-coach exists; today just confirm `getClientAccount()`'s
404-on-non-client behavior is exercised), the upsert-not-duplicate
behavior, and the "regenerating an approved brief resets status to draft"
rule from §1.

## 4. UI

**Coach side — `app/clients/[accountId]/page.tsx`:** new `CoachBrief`
client component (`components/CoachBrief.tsx`), same shape as `components/
WeeklyAnalysis.tsx` (`useState` for content/busy/error, `fetchJson` from
`lib/client-fetch.ts`) but with:
- An editable `<textarea>` for the draft content (not just
  `whitespace-pre-wrap` display — the coach needs to actually edit it,
  per the PRD's "lightweight confirm/override, not a full rewrite flow").
- "Generate brief" / "Regenerate" button (mirrors `WeeklyAnalysis`'s
  copy pattern).
- "Approve" button, disabled until a draft exists; shows an "Approved
  {date}" state once `status === 'approved'`, with the textarea still
  editable (re-editing after approval doesn't unapprove it — see §1).
- The AI-assisted badge from Phase 3's companion spec,
  `specs/phase-4-ai-transparency.md` — build these two specs' UI pieces
  together, not the brief panel first and the badge bolted on after.

**Client side (lower priority — see "Scope decisions"):** on `app/
page.tsx`, alongside the existing dashboard cards, a new read-only card
rendered only when an `approved` `coach_briefs` row exists for the current
week — "This week from your coach," plain rendered text, the same
AI-assisted badge, no edit controls (the client doesn't edit a coach's
brief).

## Recommended sequencing

1. Schema + migration (§1) — `drizzle-kit generate`, review the SQL,
   migrate.
2. `generateCoachBrief()` + tests (§2).
3. API routes + tests (§3).
4. Coach-side UI (§4, first half) — this alone is enough to demo the full
   "AI drafts, human approves" story on the coach dashboard.
5. Client-side visibility (§4, second half) — cut first if the demo date
   is close.

## Explicitly deferred

- **Real scheduling.** A Vercel cron (or similar) auto-generating drafts
  weekly. The on-demand endpoint built here is exactly what a scheduled
  job would call — adding the schedule later is additive, not a rewrite.
- **Reconciling this with the existing client-facing Weekly Analysis
  feature.** Named as a real inconsistency above; not resolved here.
- **Multi-coach scoping** on the new route/table — same deliberate,
  documented YAGNI as everywhere else in this codebase (`specs/
  client-accounts.md`, `specs/phase-2.5-coach-dashboard.md`) until a second
  coach account actually exists.

## Test plan summary (TDD — write these first, per repo convention)

- `generateCoachBrief()` grounds its prompt in the real `WeekStats`/client
  name it's given (§2).
- `POST .../brief` creates a draft; a second `POST` for the same week
  replaces it, not duplicates it (§1, §3).
- `PUT .../brief` with `approve: true` sets `status`/`approvedAt`; without
  it, edits content only.
- Regenerating (`POST`) an approved brief resets `status` to `'draft'` and
  clears `approvedAt`.
- `getClientAccount()`'s existing 404-on-non-client behavior is exercised
  through the new routes (regression coverage, not new behavior).
